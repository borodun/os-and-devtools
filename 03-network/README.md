# Сетевой квест

Ты устраиваешься в компанию «ОСИ», занимающуюся администрированием сети в университете.
Чтобы устроиться, тебе нужно пройти техническое задание в тестовой сети компании.
У тебя есть доступ к сети с одного узла `you`. Все остальные узлы заходить **нельзя**.

После каждого этапа служба отвечает строкой вида `FLAG{...}` (назовём её
**фрагментом**). Создай файл `flags.txt` рядом с этим файлом и копируй в него
каждый фрагмент целиком, так, как его напечатала служба. Не изменяй значения
и не собирай их сам. Содержимое файла должно выглядеть следующим образом:

```
F1: FLAG{...}
F2: FLAG{...}
F3: FLAG{...}
F4: FLAG{...}
F5: FLAG{...}
F6: FLAG{...}
F7: FLAG{...}
F8: FLAG{...}
```

## Запуск стенда

В папке с лабораторией выполни на хосте:

```
./generate.py
```

Скрипт создаст и запустит стенд (несколько контейнеров: твой узел, узел node,
ядро core и службы серверной). После этого:

```
docker compose exec you bash
```

Эта команда откроет оболочку на узле `you`. Все команды этапов выполняются
там. Выйти из оболочки: `Ctrl-D`. Вернуться в неё: та же команда.

## Подсказки

```
./hints.py <этап> [уровень]     # этапы: 1..8; уровни: 1, 2, 3
```

Уровень 1 — подсказка говорит, какой инструмент использовать. Уровень 2 —
команда с пропущенными параметрами. Уровень 3 — готовая команда. Каждый
следующий уровень показывают только после предыдущего.

Подсказки учитываются при оценке (см. «Оценка» в конце).

## Этап 1. «Адрес»

У твоего узла нет IP-адреса: команда `ip -br` показывает интерфейс `eth0` без
адреса. Без адреса узел не участвует в сети.

Заметка от предыдущего настройщика:

```
Узел you (1-й этаж, сеть 172.30.1.0/24):
  адрес узла:         172.30.1.10/24  на интерфейсе eth0
  шлюз по умолчанию:  172.30.1.254
  DNS-сервер:         172.30.2.20
```

Сделай по порядку:

1. Добавь адрес: `ip addr add 172.30.1.10/24 dev eth0`.
2. Добавь маршрут по умолчанию: `ip route add default via 172.30.1.254 dev eth0`.
3. Запиши DNS-сервер в файл `/etc/resolv.conf` (строка `nameserver 172.30.2.20`).

Проверка: `ping -c1 172.30.1.20` — должен быть ответ (узел node в той же сети).

Сервер имён назначен, но пока недоступен: `ping -c1 172.30.2.20` — не
отвечает. Причина та же, что и в этапе 3.

Затем соедини службу узла node: `nc 172.30.1.20 8888`. Служба спросит, кто
у тебя шлюз по умолчанию. Ответь IP-адресом из заметки (одной строкой). В
ответ придёт фрагмент — запиши его как **F1**.

Обсуждение: зачем узлу нужен IP-адрес и маска `/24`, куда ведёт маршрут по
умолчанию, что делает `/etc/resolv.conf`.

## Этап 2. «Соседи»

Устройства в одной сети обмениваются кадрами напрямую. У каждого устройства
есть MAC-адрес — аппаратный адрес на уровне кадра.

Твоя задача: узнать **свой MAC-адрес** и **MAC-адрес шлюза** (172.30.1.254),
затем отправить оба в службу node (`nc 172.30.1.20 8888`):

- 1-й строкой — свой MAC-адрес;
- 2-й строкой — MAC-адрес шлюза.

Если ответ верный — служба пришлёт фрагмент **F2**. Если нет — служба
повторит вопрос. Подсказка (уровень 1) скажет, какие команды показывают
MAC-адреса.

Обсуждение: что такое MAC-адрес, что такое ARP, как заполняется таблица
`ip neigh`, зачем при ping по IP-адресу кадр несёт MAC-адрес.

## Этап 3. «Путь»

Теперь у узла есть адрес и маршрут по умолчанию, но ping в серверную
(172.30.2.10) не проходит.

Причина: в таблице маршрутов остался **лишний маршрут** от предыдущего
настройщика — он отправляет трафик в сеть 172.30.2.0/24 через несуществующий
адрес 172.30.1.99. В таблице маршрутов узла должно остаться только:
сеть 172.30.1.0/24 (твой этаж) и маршрут по умолчанию через 172.30.1.254.

1. Посмотри таблицу маршрутов: `ip route`.
2. Удали лишний маршрут в 172.30.2.0/24 (команда — в подсказке).
3. Проверь: `ping -c1 172.30.2.10` — должен быть ответ;
   `traceroute 172.30.2.10` — ровно 2 хопа (172.30.1.254 — ядро, 172.30.2.10).
4. Сервер имён теперь тоже достижим: `ping -c1 dns.osi.local` — по **имени**,
   не по адресу (сервер имён назначен в этапе 1). Должен быть ответ.

Затем служба node (`nc 172.30.1.20 8888`) снова спросит, какой у тебя шлюз по
умолчанию. Ответь IP-адресом — получишь фрагмент **F3**.

Обсуждение: таблица маршрутов, правило «более конкретный маршрут важнее
менее конкретного», что такое хоп. Вопрос: что происходит с TTL пакета на
каждом хопе и как traceroute это использует?

## Этап 4. «Канал»

В серверной две службы, каждая ждёт ровно 10 коротких сообщений:

| Служба | Протокол | Адрес       | Порт |
| ------ | -------- | ----------- | ---- |
| msg-u  | UDP      | 172.30.2.30 | 9009 |
| msg-t  | TCP      | 172.30.2.31 | 9010 |

Порт — номер, который отличает службы на одном узле. UDP **не** гарантирует
доставку: часть сообщений потеряется. TCP **гарантирует** доставку: потерянные
сообщения передаёт заново.

1. Отправь 10 коротких сообщений в службу msg-u. Текст сообщений — любой;
   удобно пронумеровать (`msg-1`, `msg-2`, …, `msg-10`), чтобы потом увидеть,
   какие именно потерялись. Служба отвечает `принято: …` на каждое
   **полученное** сообщение — посчитай, сколько ответов пришло.
2. Отправь те же 10 сообщений в службу msg-t (все 10 в одной сессии, по одной
   строке). Она тоже отвечает `принято: …` на каждую строку — посчитай и их.
3. Сравни: на сколько сообщений каждая служба ответила, сколько времени это
   заняло и почему так.

После получения всех 10 сообщений msg-t пришлёт фрагмент **F4**.

Обсуждение: почему TCP «догоняет» потерю каждого третьего пакета, а UDP —
нет; где происходит повторная передача — в канале или в узле.

## Этап 5. «Имя»

Узлы можно адресовать не только по IP, но и по имени. Сервер имён (DNS)
переводит имена в IP-адреса. Сервер имён назначен твоему узлу в этапе 1
(файл `/etc/resolv.conf`) — теперь используем его.

1. Узнай, какому IP-адресу соответствует имя `web.osi.local`.
2. Посмотри имя `vault.osi.local`: это запись CNAME — «ссылка» на другое
   имя. Узнай, на какое имя она указывает.
3. Фрагмент **F5** лежит в записи TXT имени `key.osi.local` (TXT — текстовая
   запись). Получи этот текст и запиши его в `flags.txt`.

Обсуждение: записи A, TXT и CNAME; почему CNAME — это «ссылка», а не «копия».
Вопрос: что делает `dig` и зачем в нём `+short`?

## Этап 6. «Страница»

Узел 172.30.2.10 отдаёт веб-страницу. Открой её: `http://172.30.2.10/`.
На странице найдешь строку «Служебный вход» — адрес служебного ресурса.

Служебный вход открывается, только если в запросе есть заголовок
`X-Handshake` со значением **фрагмента F4** (из этапа 4). Заголовок — это
строка запроса вида «имя: значение».

1. Открой адрес служебного входа, добавив заголовок `X-Handshake` со
   значением F4 (как именно — подсказка).
2. Служба ответит фрагментом **F6** — запиши его.

Если открыть адрес без заголовка (или с неверным значением) — будет ответ
403 «запрещено», значит что-то неверно.

Обсуждение: из чего состоит HTTP-запрос (метод, путь, заголовки), что такое
ответы 200, 403, 404; почему `X-Handshake` передаётся заголовком, а не
параметром в адресе.

## Этап 7. «Кадры»

После этапа 3 служба node (`nc 172.30.1.20 8888`) ждёт ещё один ответ: она
спросит MAC-адрес **отправителя** и MAC-адрес **получателя** кадра, который
летел на узел node.

Чтобы увидеть кадры, используй инструмент захвата `tcpdump`. Он должен
работать, пока ты шлёшь `ping`, поэтому запускаем его фоном: знак `&` в конце
команды означает «запусти команду и отпусти — терминал останется свободным
для твоих команд».

Выполни по порядку:

1. Запусти запись кадров в фоновом режиме. Параметр `-c 2` — «остановиться
   самому после 2 кадров», запись `> /tmp/cap 2>&1` — «всё, что он напишет,
   положить в файл `/tmp/cap`»:

   `tcpdump -e -i eth0 icmp -c 2 > /tmp/cap 2>&1 &`

2. Отправь ping, чтобы кадры появились: `ping -c1 172.30.1.20`.
3. Подожди и посмотри запись: `sleep 2`, затем `cat /tmp/cap`.

Если в `/tmp/cap` нет строк с кадрами — повтори шаги 1–3 ещё раз: сначала
запись, потом ping.

В записи найди строку `ICMP echo request`. В ней MAC-адрес **перед знаком
`>`** — отправитель (это ты), MAC-адрес **после знака `>`** — получатель
(это node).

Теперь подключись к node (`nc 172.30.1.20 8888`): она спросит про кадр —
отправь две строки: сначала MAC отправителя, потом MAC получателя. Запиши
полученный фрагмент как **F7**.

Обсуждение: инкапсуляция — где в кадре лежат MAC-адреса, а где IP-адреса;
почему у кадра, летящего на соседний узел, MAC-получатель — MAC соседа, даже
если IP-адрес назначения «далеко».

## Этап 8. «Двери»

У узла node (172.30.1.20) открыт ещё один порт, кроме 8888. Найди его
(инструмент — в подсказке), затем подключись к нему: `nc 172.30.1.20 <порт>`.
Служба пришлёт фрагмент **F8** — запиши его.

Обсуждение: что такое сканирование портов, почему порты называют «дверями»
узла.

## Сдача

Когда всё готово, убедись, что в `flags.txt` стоят все фрагменты (формат —
в начале файла). Пока стенд запущен, выполни на хосте:

```
./check.py
```

Скрипт пересчитает фрагменты по живому стенду, сверит их с твоим
`flags.txt` и выведет оценку. Вывод не содержит ожидаемых значений.

Затем — **обязательный финальный шаг**: разбери стенд:

```
./clean.py
```

Без этого контейнеры останутся запущенными и будут занимать память. Файлы
`flags.txt` и `.hints` при этом не удаляются — по ним преподаватель ставит
оценку.

## Оценка

Все 8 этапов обязательны.

| Оценка | Условие                                                                      |
| ------ | ---------------------------------------------------------------------------- |
| 5      | все 8 этапов, подсказки не использовались или использовался только уровень 1 |
| 4      | все 8 этапов, подсказки не выше уровня 2                                     |
| 3      | все 8 этапов выполнены (любые подсказки)                                     |
| 2      | выполнено меньше 8 этапов (в том числе ноль)                                 |
