# Лабораторная работа. Сборка и запуск многоконтейнерного приложения

**Тема:** GCC, Make, статические библиотеки, Dockerfile, Docker Compose.

## 1. Цель работы

Организовать сборку многокомпонентного проекта на C и запуск его частей
в Docker-контейнерах.

Программы на C уже написаны. **Изменять файлы `.c` и `.h` и корневой
`Makefile` не нужно.** Необходимо написать только Makefile отдельных
компонентов и конфигурацию Docker (список в разделе 4).

## 2. Описание системы

Проект включает три приложения:

- **backend** — HTTP-сервер. В ответ на `GET /` возвращает
  `Hello from <имя> (request #N)`, где N — счётчик запросов, обработанных
  этим экземпляром. В заголовке ответа есть `X-Backend: <имя>`.
- **balancer** — принимает HTTP-запросы и по очереди направляет их двум
  backend-серверам (Round Robin). В журнал пишет, куда маршрутизирует
  каждый запрос.
- **loadgen** — отправляет запросы балансировщику, измеряет время ответа
  и записывает результаты в CSV; в конце печатает статистику:
  число успешных запросов и min/avg/max задержки.

В итоговой системе должны работать четыре контейнера: два экземпляра
`backend`, один `balancer`, один `loadgen`.

```text
                       Компьютер
                  http://localhost:8080
                           |
                           v
                       balancer
                       порт 8080
                       /       \
                      v         v
               backend-1     backend-2
                порт 9000     порт 9000

                       loadgen
                          |
                          v
                   balancer:8080
                          |
                  результаты в CSV
```

## 3. Структура проекта и зависимости

```text
.
├── Makefile                 # Готовый, изменять не нужно
├── include/
│   ├── net.h
│   ├── http.h
│   └── utils.h
├── lib/
│   ├── net.c
│   ├── http.c
│   └── utils.c
└── apps/
    ├── backend/
    │   ├── main.c
    │   ├── handler.c
    │   └── handler.h
    ├── balancer/
    │   ├── main.c
    │   ├── router.c
    │   └── router.h
    └── loadgen/
        ├── main.c
        ├── stats.c
        └── stats.h
```

Общие функции объявлены в `include/` и реализованы в `lib/`. Из
`net.c`, `http.c` и `utils.c` необходимо собрать **статическую библиотеку**
`build/lib/libcommon.a`.

Все три приложения используют эту библиотеку:

```text
     lib/net.c  lib/http.c  lib/utils.c
                  |
                  v
       build/lib/libcommon.a
            /     |     \
           v      v      v
       backend  balancer  loadgen
```

| Приложение | Собственные исходники | Результат сборки         |
| ---------- | --------------------- | ------------------------ |
| backend    | `main.c`, `handler.c` | `apps/backend/backend`   |
| balancer   | `main.c`, `router.c`  | `apps/balancer/balancer` |
| loadgen    | `main.c`, `stats.c`   | `apps/loadgen/loadgen`   |

**Порядок сборки:** сначала общая библиотека, затем приложения.
Корневой `Makefile` уже задаёт этот порядок.

## 4. Какие файлы необходимо написать

Всего **9 файлов**:

| Файл                       | Назначение                                     |
| -------------------------- | ---------------------------------------------- |
| `lib/Makefile`             | Сборка статической библиотеки `libcommon.a`    |
| `apps/backend/Makefile`    | Сборка `backend` с общей библиотекой           |
| `apps/balancer/Makefile`   | Сборка `balancer` с общей библиотекой          |
| `apps/loadgen/Makefile`    | Сборка `loadgen` с общей библиотекой           |
| `apps/backend/Dockerfile`  | Образ backend                                  |
| `apps/balancer/Dockerfile` | Образ balancer                                 |
| `apps/loadgen/Dockerfile`  | Образ loadgen                                  |
| `compose.yaml`             | Запуск и настройка четырёх контейнеров         |
| `.dockerignore`            | Исключение ненужных файлов из контекста сборки |

### 4.1. Требования к дочерним Makefile

- `lib/Makefile` должен собирать общую библиотеку из трёх исходных
  файлов и размещать её в `build/lib/libcommon.a` относительно корня проекта.
- Каждый Makefile приложения должен собирать собственный исполняемый
  файл из двух `.c` и связывать его с общей библиотекой.
- Сборка должна находить заголовочные файлы из корневого каталога `include/`.
- Все четыре дочерних Makefile должны поддерживать цели `all` и `clean`.
- После `make` из корня должны создаваться библиотека и три исполняемых
  файла; после `make clean` результаты сборки должны удаляться.

**Переменные окружения:** используйте `CC` для компилятора и `CFLAGS`
для параметров компиляции так, чтобы их значения можно было переопределить
через окружение при запуске `make` (например,
`CC=gcc CFLAGS="-Wall -Werror" make`). Если переменные не заданы извне,
сборка должна работать со значениями по умолчанию.

Разрешается любой синтаксис Makefile (простые и рекурсивные переменные,
шаблонные правила, функции, каталоги объектных файлов) — главное, чтобы
сборка работала и цели `all`/`clean` вели себя корректно.

### 4.2. Требования к Dockerfile

Для каждого приложения — отдельный Dockerfile с **двухэтапной сборкой**:

1. В первом этапе выполняется сборка общей библиотеки и соответствующего
   приложения.
2. Во втором этапе находится только готовый исполняемый файл и
   необходимые компоненты среды исполнения, **без компилятора** и
   инструментов сборки.

Можно использовать образы `gcc:13-bookworm` и `debian:bookworm-slim`.

Общая библиотека и заголовочные файлы находятся **вне** каталогов
отдельных приложений. Это нужно учесть при выборе контекста сборки
и при `.dockerignore`.

### 4.3. Требования к Docker Compose

Опишите сервисы с именами: `backend-1`, `backend-2`, `balancer`, `loadgen`.
Два backend используют **один и тот же Dockerfile**, но работают в
отдельных контейнерах.

**Порты:**

| Сервис      | Порт внутри контейнера | Доступ с компьютера          |
| ----------- | ---------------------- | ---------------------------- |
| `backend-1` | `9000`                 | Не публиковать               |
| `backend-2` | `9000`                 | Не публиковать               |
| `balancer`  | `8080`                 | Опубликовать на порту `8080` |
| `loadgen`   | Входящий порт не нужен | Не публиковать               |

Внутри сети Docker Compose используйте имена сервисов для обращения
к другим контейнерам. Для `loadgen` настройте сохранение CSV в локальный
каталог `results/` (каталог `/results` контейнера должен соответствовать
`results/` в корне проекта). Предусмотрите порядок запуска: сначала
backend, затем balancer, затем loadgen.

**Переменные окружения приложений:**

| Сервис      | Переменная      | Значение                        |
| ----------- | --------------- | ------------------------------- |
| `backend-1` | `PORT`          | `9000`                          |
| `backend-1` | `SERVER_NAME`   | `backend-1`                     |
| `backend-2` | `PORT`          | `9000`                          |
| `backend-2` | `SERVER_NAME`   | `backend-2`                     |
| `balancer`  | `PORT`          | `8080`                          |
| `balancer`  | `BACKENDS`      | `backend-1:9000,backend-2:9000` |
| `loadgen`   | `TARGET_HOST`   | `balancer`                      |
| `loadgen`   | `TARGET_PORT`   | `8080`                          |
| `loadgen`   | `REQUEST_COUNT` | `1000`                          |
| `loadgen`   | `OUTPUT_FILE`   | `/results/result.csv`           |

## 5. Проверка работоспособности

Все проверки выполняются из корня проекта.

### 5.1. Локальная сборка

Выполните `make` и убедитесь, что созданы:

```text
build/lib/libcommon.a
apps/backend/backend
apps/balancer/balancer
apps/loadgen/loadgen
```

Проверьте, что `make clean` удаляет результаты, а повторный `make` снова
собирает проект. Отдельно проверьте, что
`CC=... CFLAGS="..." make` использует переданные значения при новой сборке.

### 5.2. Запуск контейнеров

Соберите образы и запустите систему через Docker Compose. Проверьте
состояние контейнеров и журнал `loadgen`. После завершения нагрузки
`loadgen` должен завершиться успешно (код 0), остальные три контейнера —
продолжить работу.

Перед первым запуском создайте каталог для результатов сами
(`mkdir results`): если каталог создаст Docker, он будет принадлежать
root, и `clean.py` не сможет удалить его без `sudo`.

Ожидаемые строки в журнале:

```text
Requests: 1000, successful: 1000, failed: 0
Latency ms: min=... avg=... max=...
Saved to /results/result.csv
```

### 5.3. Работа балансировщика

```bash
curl http://localhost:8080/
curl http://localhost:8080/
curl http://localhost:8080/
```

Ответы должны чередоваться:

```text
Hello from backend-1 (request #...)
Hello from backend-2 (request #...)
```

Первый ответ может принадлежать любому backend, если балансировщик уже
обслуживал запросы. Счётчики `#N` у backend-1 и backend-2 должны расти
примерно поровну.

### 5.4. Результаты нагрузки

Файл `results/result.csv` на компьютере: **1001 строка** (заголовок и
1000 результатов), заголовок:

```csv
request_id,backend,latency_ms,status
```

При последовательном генераторе — по 500 ответов от каждого backend,
статус всех строк — 200.

### 5.5. Изменение конфигурации

Измените `REQUEST_COUNT` с `1000` на `100` и повторно запустите
**только loadgen** без пересборки образов. В результирующем CSV должно
быть **101 строка**.

## 6. Бонусные задания

### Б1. Healthcheck

Настройте для обоих backend healthcheck, который проверяет, что процесс
слушает свой порт, и подключите balancer к backend через
`depends_on` с условием «ожидать работоспособность» (`service_healthy`).
После `docker compose up` контейнеры backend должны становиться
`healthy`. Учтите: в итоговом образе **нет curl** — подумайте, чем
проверить порт имеющимися средствами.

### Б2. Маленький образ

Сделайте так, чтобы итоговые образы были поменьше (менее 150 МБ).
Посмотрите, что именно занимает место: `docker compose images`,
`docker history <образ>`.

### Б3. Конфигурация из `.env`

Вынесите изменяемые значения (например, `REQUEST_COUNT`, порты) в файл
`.env` в корне проекта и используйте подстановку переменных
(`${ПЕРЕМЕННАЯ}`) в `compose.yaml`, чтобы менять конфигурацию
из одного места.

## 7. Самопроверка и сдача

- `./check.py` — проверяет, что всё собрано и работает. Печатает
  по каждому пункту есть/нет.
- `./clean.py` — убирает результаты сборки, `results/` и
  останавливает контейнеры.
- **Сдача:** когда `check.py` зелёный — позовите преподавателя и покажите
  работающую систему: сборку `make`, запущенные контейнеры, `curl`
  к балансировщику и CSV. Покажите и объясните, как устроена ваша
  сборка (Makefile и Dockerfile).
